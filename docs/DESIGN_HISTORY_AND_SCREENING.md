# スコア推移の履歴保存 × 複数銘柄一括スクリーニング 設計方針書

Sprint34以降、この2機能に着手する際は、実装前に必ずこの文書を読むこと。
docs/AI_HANDOVER.mdがSprintごとの「実装した記録」であるのに対し、この文書は
「なぜそう設計したか」という中心となる考え方を記した、Sprintをまたいで
更新されるべき恒久的な設計方針書である。個別Sprintの実装内容は従来通り
docs/AI_HANDOVER.mdに追記するが、設計思想そのものが変わった場合はこの文書を
更新すること。

# 1. なぜこの2機能を一緒に設計するのか

「スコア推移の履歴保存」（同一銘柄を時間軸で追う）と「複数銘柄一括スクリーニング」
（同時点で複数銘柄を横断的に見る）は、一見すると別物に見えるが、
実装の土台になる部分が共通している。

- どちらも「複数ティッカーに対してcreate_analysis_bundle相当の処理をループで
  実行する」という重い処理を扱う（Sprint29〜30で最適化したPortfolio/Watchlistの
  rows構築と同種の負荷特性）
- どちらも、Sprint1〜33を通じて一度も必要にならなかった「session_stateを
  超えた永続化」が前提になる（ブラウザを閉じても消えないデータ）

この2点が今回初めて共通の基盤を必要とするため、個別に場当たり的に作ると
高い確率で重複実装（ルール14違反）になる。先に土台となる考え方を固めてから
着手する。

# 2. これから先も使える中心となった考え方

## 原則A：永続化層は独立した薄いレイヤーとして新設する（src/storage）

現状（Sprint33時点）、このアプリが保持する状態はすべてst.session_state上に
あり、ブラウザを閉じれば消える。履歴保存・スクリーニング結果の保存は、
このアプリで初めて「セッションをまたいで残るデータ」を扱う機能になる。

- 新設する`services/src/storage/`に、保存・取得のインターフェースだけを
  切り出す（例：`save_score_snapshot()` / `load_history(ticker)` /
  `save_screening_run()` / `load_screening_runs()`）。
- 「何を保存するか」（history/screening側のロジック）と「どう保存するか」
  （ファイル形式・パス）を分離しておく。将来ストレージ形式を変える場合
  （JSON→SQLite等）に、呼び出し側を書き換えずに済むようにするため。
- PROJECT_RULES.mdのディレクトリ構成（analysis/engines/data/ai/ui/report）に
  「保存」という責務がまだ無いため、新カテゴリとして追加する。
  PROJECT_RULES.mdにもルールとして追記すること（後述4章）。

## 原則B：「単一銘柄の時系列」と「複数銘柄の横断」は別軸として扱う（ルール24・25の考え方の延長）

ルール24・25は、Portfolio Risk（複数銘柄・共通フォーマットでスコア化）と
Watchlist Insights（複数銘柄・スコア化しない集計）という「評価単位が
単一銘柄の190点満点スコアと異なるものは、analysis_bundle/overall_evalに
混ぜ込まない」という判断基準を確立した。今回の2機能もこれに従って
整理すると、以下のようになる。

- **履歴保存**：あくまで「1銘柄」を評価単位とする。時間軸に沿って
  同じ190点満点スコア（overall）を並べているだけであり、Portfolio Risk・
  Watchlist Insightsとは性質が異なる。既存のanalysis_bundle/overall_evalの
  計算結果を「保存する」だけで、計算ロジック自体には一切手を入れない。
- **一括スクリーニング**：評価単位は「複数銘柄」。Watchlist Insightsと
  同じく、個々の銘柄のanalysis_bundleをループで作り、その結果を横断的に
  集計・ランキングする独立機能として実装する。analysis_bundle/overall_eval
  自体には組み込まない。
- スクリーニングを「スコア化してランキングする」のか「Watchlist Insights
  のように集計・参考表示にとどめる」のかは、ルール25の判断基準
  （点数化して優劣を決める性質の機能か／集計に留める機能か）に従い、
  実装前にきたに確認すること。今回は各銘柄が既にoverall_score（190点満点）
  を持っているため、Portfolio Riskのように「新たに10点満点のスコアを
  作る」必要はなく、既存のoverall_scoreでソートするだけで足りる可能性が
  高い。この場合、ルール25でいう「独立した専用の戻り値形式でよい」
  パターンに近い。

## 原則C：重い処理のキャッシュは既存パターン（_cache_by_signature）を再利用する

Sprint29〜30で、Portfolio/Watchlistの銘柄一覧構築を「signature + TTLで
session_stateにキャッシュする」`_cache_by_signature()` / `_build_rows_cached()`
というパターンを確立済み。一括スクリーニングも「複数ティッカーをループで
処理する」という点で全く同じ負荷特性を持つため、このパターンをそのまま
再利用する（ルール14）。新しいキャッシュの仕組みを作らないこと。

ただし、現状`_cache_by_signature()`はapp.py内に定義されており、これは
本来「app.pyへ分析ロジックを書かない、Controllerのみ」というルール4の
精神からするとやや逸脱している（ロジックというより横断的なユーティリティ
ではあるが）。履歴保存・スクリーニングの両方から使う汎用ヘルパーになる
ことで利用箇所がさらに増えるため、このタイミングで`src/engines/`か
新設する`src/storage/`配下に切り出すかどうかは、実装着手前にきたに
相談すること（勝手に動かさない。既存のPortfolio/Watchlist側の呼び出しを
壊さないよう、移動する場合は互換ラッパーを残すルール3・17に従う）。

## 原則D：履歴保存は「毎回フルモード分析を強制しない」

フルモード分析はAI呼び出し（Gemini）を含み、時間もAPIコストもかかる。
履歴保存機能が「保存のたびに毎回フルモードで再計算」を要求する設計に
なると、単なる時系列記録のためだけに余計なAI呼び出しコストが発生する。

- 履歴に保存するのは、AIの定性分析全文ではなく、overall（190点満点の
  スコア・グレード・BUY/WATCH/PASS判定）のような軽量なサマリーのみに
  絞る。
- クイック/標準モードで解析した場合、一部項目（MOAT・ROIC等）が未評価
  （0点扱い）になる点はSprint32で対応した表示上の注記と同じ注意が必要。
  履歴データにも「どのモードで評価したか」を必ず記録し、後で時系列
  グラフを見たときに「モードが違うから比較できない値が混ざっている」
  ことが分かるようにする。

## 原則E：スクリーニング結果も、保存するのは軽量なサマリーのみ

一括スクリーニングは対象銘柄数が多くなりうる（ウォッチリスト全体、
あるいは自由入力の銘柄リスト）。全銘柄のanalysis_bundle全体（AIの
定性分析テキストを含む）をまるごと保存・保持すると、メモリ・ストレージ
共に膨らみやすい。原則12（分析モジュール共通形式：id/title/score/
max_score/rating/summary/details/warnings）はあくまで「1回の分析結果を
その場で表示する」ための形式であり、複数銘柄×複数時点を保存する
スクリーニング結果には、以下のような軽量な形式を別途定義する。

```
{ticker, evaluated_at, total_score, max_score, grade, decision, mode}
```

これは履歴保存（原則D）で保存する1件分のデータ構造とも共通にできる
（同じ「銘柄×時点」のスナップショットという性質を持つため）。
共通データモデルとして1箇所にまとめ、履歴保存機能とスクリーニング機能の
両方から使うことで、ここでも重複実装を避ける（ルール14）。

## 原則F：永続化データはgit管理対象に含めない

このプロジェクトは、AIサンドボックス環境で作業しgit bundleでコードだけを
きたのローカルに渡す、という特殊な運用になっている（本文書冒頭・
AI_HANDOVER.md参照）。履歴保存・スクリーニング結果はきた個人の分析データ
であり、ソースコードではない。保存先ディレクトリ（例：`data/history/`等）
は`.gitignore`に追加し、git管理・bundle配布の対象から明確に外すこと。
サンドボックス側で作ったテスト用データがbundleに紛れ込んだり、逆に
きたのローカルの実データがAIに送られたりしないようにするための、
この運用形態特有の注意点である。

# 3. データモデル（たたき台。実装着手時にきたと最終確認する）

```
ScoreSnapshot:
  ticker: str
  evaluated_at: ISO8601 timestamp
  mode: "quick" | "standard" | "full"
  overall_score: int        # 190点満点
  grade: "S"|"A"|"B"|"C"|"D"
  decision: "BUY"|"WATCH"|"PASS"
  buffett_score: int        # 100点満点（内訳の代表値として。任意）
```

- 履歴保存：ある1銘柄について、`ScoreSnapshot`を時系列で複数件保持する
- スクリーニング：ある1回の実行について、複数銘柄ぶんの`ScoreSnapshot`
  （evaluated_atは実行時点で全銘柄共通）をまとめて保持する

この2つは同じ`ScoreSnapshot`という単位の「集め方」が違うだけ、という
整理にできれば、保存フォーマット・保存関数を完全に共通化できる
（原則Eの続き）。

# 4. 段階的な実装ステップ（提案。順番はきたと相談して決定する）

1. **永続化層の新設**（`src/storage/`、`ScoreSnapshot`の保存・取得のみ。
   UIには一切繋がない状態でまず健全性を確認する）
2. **履歴保存**（単一銘柄、分析実行時に`ScoreSnapshot`を1件保存する
   導線 + 時系列で並べて表示するUI）
3. **複数銘柄一括スクリーニング**（Watchlist Insightsと同じくanalysisを
   ループで実行し、`ScoreSnapshot`のリストとしてランキング表示。
   ステップ1の永続化層を再利用し、実行結果を保存する場合はここで配線）
4. **UI仕上げ**（履歴の折れ線グラフ、スクリーニング結果のソート・
   フィルタ等）

ステップ1を必ず最初に独立させるのは、履歴保存・スクリーニングの
どちらから手を付けても土台が同じであることを実装レベルでも保証するため。

# 5. 実装着手前にきたに確認すること（未確定事項）

- ストレージ形式：JSONファイル（ティッカーごと1ファイル等）か、
  SQLiteか。運用形態（Windows・ローカル・単一ユーザー）を考えると
  JSONファイルで十分な可能性が高いが、要件（検索・集計のしやすさ）
  次第では最初からSQLiteの方が良い場合もある
- 履歴保存のタイミング：分析を実行するたびに自動保存するか、
  明示的な「保存」ボタンを押したときだけ保存するか
  （自動保存だと同じ銘柄を何度も見ただけでノイズが増える懸念がある）
- スクリーニング対象銘柄の入力方法：ウォッチリスト登録銘柄と連動する
  のか、自由入力（カンマ区切り等）を受け付けるのか、あるいは両方か
- スクリーニングをスコア化・ランキングする機能として位置づけるか
  （原則B参照。既存のoverall_scoreを流用するだけなら追加のスコア設計は
  不要と考えられる）

# 6. PROJECT_RULES.mdへの追記案

上記の設計が固まり実装に着手する段階になったら、以下をPROJECT_RULES.mdに
ルールとして追記すること（このドキュメント自体はルールブックの代わり
ではなく、ルール化する前の設計検討記録という位置づけ）。

- 永続化（保存・取得）ロジックは `src/storage` に置く
- 保存データ（history/screening結果）はgit管理対象に含めない
  （`.gitignore`で除外する）
- 「銘柄×時点」のスナップショットを扱う機能は`ScoreSnapshot`形式を
  共通で使う（履歴保存・スクリーニングに限らず、今後同種の機能を
  追加する場合も踏襲する）
